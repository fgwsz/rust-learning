# 编译运行
## `rustc`编译运行单个源文件
```bash
#创建项目目录
mkdir rustc_hello_world
#进入项目目录
cd rustc_hello_world
#创建编辑Rust源文件
gvim main.rs
```
向`main.rs`写入的文件内容如下:
```rust
fn main(){
    println!("hello world!");
}
```
编辑完成之后保存,运行如下指令,使用`rustc`工具编译源码生成可执行文件:
```bash
rustc main.rs
```
运行完成之后会生成了如下的目录结构:
```
rustc_hello_world/
│ main.exe
│ main.pdb
│ main.rs
```
其中`main.exe`就是编译生成的可执行文件.

可以通过直接运行它,来观察运行结果.
```bash
./main.exe
```
运行结果显示如下:
```
hello world!
```
## `cargo`编译运行多源文件项目
`cargo`是`Rust`工具链中用来进行项目管理和包管理的工具.

### `cargo new`创建项目模板
使用`cargo new [项目名称]`可以快速创建一个空项目模板.

```bash
#创建名为cargo_hello_world的空项目
cargo new cargo_hello_world
```
运行结果如下:
```
    Creating binary (application) `cargo_hello_world` package
note: see more `Cargo.toml` keys and their definitions at https://doc.rust-lang.org/cargo/refere
nce/manifest.html
```
此时创建的项目目录文件结构如下:
```
cargo_hello_world/
│ src/
│ │ main.rs
│ Cargo.toml
```
`Cargo.toml`是项目描述文件.它使用`TOML`语言.

其中默认生成的`Cargo.toml`文件内容为:
```toml
[package]
name = "cargo_hello_world"
version = "0.1.0"
edition = "2024"

[dependencies]
```
`[package]`标签页中记录了如下信息:

`name`:项目名称

`version`:版本

`edition`:`Rust`语言版本

`[dependencies]`标签用于记录项目依赖的第三方库信息.

其中默认生成的`main.rs`文件内容为:
```rust
fn main() {
    println!("Hello, world!");
}
```

### `cargo new`创建`Git`项目
通过上述的说明文档,发现可以使用`cargo new`直接创建一个`Git`项目.

使用方式是:`cargo new [项目名称] --vcs=git`

这里创建如下的`Git`项目,进行测试.
```bash
cargo new git_hello_world --vcs=git
```
`cargo new`生成的项目目录文件结构如下:
```
git_hello_world/
│ .git/
│ src/
│ │ main.rs
│ .gitignore
│ Cargo.toml
```
不难发现,`--vcs=git`的作用是:

1.使用`git init`了项目目录,由此生成了`.git`文件夹

2.增加了`.gitignore`文件

其中,生成的`.gitignore`文件内容如下:
```
/target
```
这里提前说明:`target`目录用来存放项目编译生成的中间文件和可执行文件.
### `cargo build`编译生成可执行文件
在`cargo_hello_world`项目根目录,
运行`cargo build`命令,会创建一个`target/`目录和`Cargo.lock`文件.

`Cargo.lock`记录了项目依赖的库的实际版本.
```toml
# This file is automatically @generated by Cargo.
# It is not intended for manual editing.
version = 4

[[package]]
name = "cargo_hello_world"
version = "0.1.0"
```
当前库没有第三方库的依赖,暂时让`Cargo`自动去处理它好了.

`target/`目录的文件结构是这样的:
```
target/
│ debug/
│ │ .fingerprint/
│ │ build/
│ │ deps/
│ │ examples/
│ │ incremental/
│ │ .cargo-lock
│ │ cargo_hello_world.d
│ │ cargo_hello_world.exe
│ │ cargo_hello_world.pdb
│ .rustc_info.json
│ CACHEDIR.TAG
```
可执行文件生成在`target/debug/cargo_hello_world.exe`路径.

可以使用`./target/debug/cargo_hello_world.exe`运行可执行程序.
也可以使用`cargo run`命令直接调用这个可执行文件.
```
$ cargo run
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.03s
     Running `target\debug\cargo_hello_world.exe`
Hello, world!
```
### `cargo run`运行项目
如果不使用`cargo build`,
在`cargo_hello_world`项目根目录下直接使用`cargo run`会发生什么呢?
```bash
#进入项目目录
cd cargo_hello_world
#直接运行项目
cargo run
```
运行结果是这样的.
```
$ cargo run
   Compiling cargo_hello_world v0.1.0 (cargo_hello_world)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.43s
     Running `target\debug\cargo_hello_world.exe`
Hello, world!
```
项目的文件结构:
```
src/
target/
.gitignore
Cargo.lock
Cargo.toml
```
至此,发现直接使用`cargo run`和先构建`cargo build`后运行`cargo run`的方式,
两者得到的实际结果是一样的.
### `cargo check`检查代码是否可以编译通过
当开发者在开发过程中并不是每次修改源代码都要进行构建和运行,
我们期望有一种更快速的方式来检查代码是否有错误,并不希望进行冗长的构建编译运行.
`Cargo`提供了`cargo check`命令实现了这一功能.

`cargo check`命令可以检查当前项目的代码是否可以编译通过,并不会进行构建编译,
大大提升了开发效率.

下面的命令运行时间,可以直观感受到这一点.
```
$ cargo build
   Compiling cargo_hello_world v0.1.0 (cargo_hello_world)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.41s
$ cargo check
    Checking cargo_hello_world v0.1.0 (cargo_hello_world)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.09s
```
### `cargo build --release`构建发布版本
当项目最终准备好发布时,可以使用`cargo build --release`来优化编译项目.

这会在`target/release`而不是`target/debug`下生成可执行文件.

`cargo_hello_world/`目录下执行`cargo build --release`命令,
运行生成的可执行文件所在目录文件结构如下:
```
target/
│ release/
│ │ .fingerprint/
│ │ build/
│ │ deps/
│ │ examples/
│ │ incremental/
│ │ .cargo-lock
│ │ cargo_hello_world.d
│ │ cargo_hello_world.exe
│ │ cargo_hello_world.pdb
│ .rustc_info.json
│ CACHEDIR.TAG
```

`--release`选项会启用编译优化,这些优化可以让`Rust`代码运行的更快,
不过启用这些优化也需要消耗更长的编译时间.

这也就是为什么会有两种不同的配置:一种是为了开发,你需要经常快速重新构建;
另一种是为用户构建最终程序,它们不会经常重新构建,并且希望程序运行得越快越好.
